# Production readiness audit — 19 September 2026

## Root causes and scope

The live homepage HTML referenced the illustration fallback instead of media photographs. A direct live request to `/media/content/2026/09/ee76d63df2494e7a898b88fe7467da0c.webp` returned **200 image/webp**. Thus committed files were available, but committing files did not populate the independent PostgreSQL image fields. The previous template selected the placeholder for empty fields. This is evidence from public HTML, not a direct inspection of production SQL.

The local database had 18 image references, all present on disk. Git contains 57 media files. A verified registry maps 14 source photographs to their committed encoded filenames (including known duplicates). Build now links 18 default references after migrations and seeding. The registry was generated by reproducing the upload encoder and matching SHA-256 bytes against committed files. No renamed upload or guessed path is inserted.

Previously responsive markup assumed derivative files existed. It now checks actual originals/variants, emits only existing srcset URLs, and uses the existing illustration for missing originals without modifying owner records. Development now uses the same explicit image MIME handler as Render, avoiding Windows WebP MIME misdetection. Traversal, null bytes, non-image paths and missing files return 404.

The earlier homepage 404 was missing singleton content after schema migrations; migration 0006 already fixes it and remains covered by the fresh-database reproduction. Earlier startup attempted optional installation under /var/data. start.sh already only starts Gunicorn and remains unchanged. Canonical normalization and trusted Render HTTPS handling from the prior fix remain intact; dotted-host and one-hop redirect tests pass. No design rewrite or production password change was made.

Admin had no wired password-reset routes. The login now exposes Django's standard recovery flow, restricted to active staff with usable passwords, with a one-hour expiry, generic responses, CSRF protection and five requests per email per hour. Links use configured SITE_URL rather than an untrusted request host. SMTP errors do not expose details or tokens. Production no longer defaults to the console email backend.

Enquiry emails previously contained only a database ID. They now contain the submitted details and a canonical admin review link, delivered to CONTACT_NOTIFICATION_EMAIL. Saving occurs before email; delivery failure preserves the record. No visitor auto-reply is sent. There were no custom admin bulk actions to repair; native selected-row deletion and permission checks were tested.

```dotenv
# Add to enable real Brevo delivery
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=smtp-relay.brevo.com
EMAIL_PORT=587
EMAIL_HOST_USER=<SMTP-login-from-Brevo>
EMAIL_HOST_PASSWORD=<Brevo-SMTP-key-not-API-key>

DEFAULT_FROM_EMAIL=<Brevo-verified-sender-address>

# Optional
GSC_VERIFICATION=<verification-token-if-used>
HSTS_INCLUDE_SUBDOMAINS=false
HSTS_PRELOAD=false
```

Remove MEDIA_ROOT=/var/data/media while there is no disk. Remove a production console EMAIL_BACKEND or replace it with SMTP above. ENQUIRY_EMAIL remains a backward-compatible recipient fallback; remove it after moving its value to CONTACT_NOTIFICATION_EMAIL to avoid confusion. Do not add SECURE_SSL_HOST or forwarded-host environment workarounds: code derives the secure canonical host. TRUST_LOCAL_PROXY is unnecessary on Render. Render supplies RENDER=true and PORT automatically. STAGING_USER/STAGING_PASSWORD are only needed for an explicitly protected staging service. Change INDEXABLE to true only after launch/content/privacy approval.

Brevo requires a verified sender/domain and its SMTP credentials, not an API key. Render Free blocks outbound ports 25, 465 and 587; therefore the example 587 configuration needs an eligible service. Brevo also supports STARTTLS on 2525, which can be considered only after testing connectivity/delivery from the actual service. No real SMTP credentials were supplied or delivery claimed. Sources: [Render Free restrictions](https://render.com/docs/free), [Brevo SMTP integration](https://developers.brevo.com/docs/smtp-integration).

## Admin, recovery and email validation

Tests cover login/logout, staff/editor permissions, denied selected deletion, deletion affecting only selected rows, content editing reflected publicly, upload replacement and responsive encoding, dashboard, singleton controls, drafts and previews. Password tests cover active staff, excluded non-staff/inactive/unusable accounts, generic unknown-email response, valid reset, expired/invalid/reused tokens, old password rejection, new password login, CSRF, throttling and SMTP failure. Enquiry tests verify recipient/sender/body, validation, honeypot, rate limits, CSRF and preservation on SMTP failure.

Normal recovery: admin login -> Forgotten your password or username? -> registered staff email -> expiring reset link. Ensure the staff account has a current email. Unknown addresses get the same response.

Emergency recovery, authorized Render Shell only:

```bash
python manage.py shell -c "from django.contrib.auth import get_user_model; print(list(get_user_model().objects.filter(is_superuser=True).values('username', 'email', 'is_active', 'is_staff')))"
python manage.py changepassword <username>
```

Never print hashes. The password command prompts without putting the password into command history. No account was created or reset in the real databases during this audit.

- HTTPS homepage: 200, no Location header; photos visible with successful original/variant network requests.
- Direction/category/About pages: 200; unknown page: 404. Static CSS/logo: 200.
- HTTP homepage: one redirect to the correct HTTPS host; no `.com./` anywhere.
- Admin login/logout and content edit: save, check public result, restore test copy. Preview stays private.
- Admin image replacement: preview/public image works; keep a backup because uploads are ephemeral on the current plan.
- Forgot password: use a real active staff email; receive and use link, then verify it cannot be reused. Delivery requires SMTP configuration.
- Submit one labelled test enquiry: verify confirmation, PostgreSQL-backed admin record and configured inbox notification. Remove the test record after review.
- Review public contact details/privacy before indexing; then set INDEXABLE=true, run launch_check, submit sitemap.xml in Search Console and inspect representative URLs.

Live deployment status and commit SHA are reported in the final task response. Until deployed and SMTP configured, local test success is not proof of live email delivery or database access.
